# 開発・メンテナンスフロー

本プロジェクトにおけるデータ管理と開発の運用ルール。

## 1. ブランチ戦略

作業内容に応じて、以下のブランチ名で作業を切り分ける。

| ブランチ名          | 用途                                             |
| :------------------ | :----------------------------------------------- |
| `feat/data-[maker]` | 新規車種データの追加（メーカー単位で集約）       |
| `fix/data`          | 既存データの誤記・スペック修正（全メーカー共通） |
| `feat/scripts`      | バリデータやツール系の開発                       |
| `refactor/schema`   | `schema.json` の構造変更・定義見直し             |
| `feat/docs`         | ドキュメントの作成・更新                         |
| `chore/misc`        | その他、環境設定や雑務                           |

## 2. コミットプレフィックス

履歴の視認性を高めるため、以下のプレフィックスを使い分ける。

- `feat:` : 新規データの追加、新ツールの作成
- `change:` : 既存データの更新（スペック追記、画像パス変更など）
- `fix:` : データ間違いやバグの修正
- `docs:` : ドキュメントのみの変更
- `refactor:` : 構造のリファクタリング（定義変更など）
- `chore:` : 設定変更、パッケージ更新などの雑務

## 3. 基本的なメンテナンスの流れ

1. `main` から目的別のブランチを作成して作業を開始する。
2. 作業完了後、適切なプレフィックスを付けて記録。
3. リモートへ送信し、GitHub上のプルリクエスト経由で `main` へ合流させる。
   - 直接 `main` を汚さず、作業単位を明確に保つため。
